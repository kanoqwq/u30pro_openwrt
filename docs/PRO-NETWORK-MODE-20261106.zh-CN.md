# Pro 网络模式与 EN-DC 的 LTE-only 约束

## 实机定位

F50 Pro 当前包 `f50pro-r20261106.102746-g548eef39-s0edf40e4`，
Linux `6.12.94-u30pro-p1`。原厂参考采集为 MU3356 / F50ProV1.0.0B22。
用户同时报告 U30 Pro 有相同现象；本轮实机是 F50 Pro。

当前上网逻辑栈为 1，原始 `SPTESTMODE` 为 `152,3,0,20,3,1`。
通过现有 AT owner 包装一次原流程，得到：

```text
AT+SPACTCARD=1;+SP5GRAN=1  -> +CME ERROR: 3
AT+SPACTCARD=1;+SPENDC=2   -> +CME ERROR: 3
```

旧流程先写 `SP5GRAN`，尚未执行恢复自动模式的 `SPTESTMODE` 就退出，
因此后续重复点击仍留在仅 4G 状态。

只把同一逻辑栈的工作模式恢复后，`SPTESTMODE=152,152,0` 接受且回读正确，
再发同一栈的 `SP5GRAN=1`、`SPENDC=2/1` 均成功，EN-DC 分别回读 0/1。
这证明所观察的拒绝来自当前 LTE-only 状态和设置顺序，不是卡源映射写反。

还核对了两栈 EN-DC 独立：在栈 0 关闭后，栈 0 回读 0、栈 1 仍回读 1，
随后恢复栈 0。**不把这些命令改发到另一栈，也不修改 NR 主栈字段。**
原厂 `libimpl-ril.so` 的 `requestSetStandAlone` 及 EN-DC 设置路径同样通过
指定 socket 发送对应指令，未见需要改物理卡源的步骤。

## 实现

- 平台 `/etc/mu300/platform=u30pro` 覆盖 U30 Pro / F50 Pro。交互设置、
  清除锁定和开机回放共用顺序：先写并核对完整工作模式三字段，再设置 SA。
- 切到仅 4G 时不再发送当前固件拒绝的 SA setter，且不强求无意义的 SA 位
  变成 1；工作模式本身仍必须正确回读，目标卡、另一卡模式和主栈字段均保留。
- 仅 4G 下的 EN-DC 开关保存当前逻辑卡的偏好，网页明确提示待支持 5G 的模式
  生效。实际模组读值和已保存偏好分开返回，不把“已保存”伪装成模组已改变。
- 之后手动切回自动／NR 模式时恢复并核对该卡 EN-DC 偏好；开机回放也先模式、
  后 EN-DC。清除锁定仍显式恢复 EN-DC 开启并删除旧偏好。
- 读取模式失败、真正的 NR setter 拒绝、回读不一致及保存失败仍报告错误。
  Pro 模式写入前使本卡锁定缓存失效；若后续 NR setter 失败，下一次读取展示
  实际的部分生效结果，不继续显示旧缓存。不用无限重试或重启基带掩盖拒绝。
- 控制继续使用原 SPACTCARD、命令 owner、互斥及 SFUN 流程，不向 NR0 塞控制。
  前后卡源 GPIO 和数据卡记录逐字节相同；没有修改 NV／IMEI、刷写或重启整机。

MU300 与 E5 静态上也存在原顺序，但用户实测 MU300 没有此问题，E5 无本轮
同类实机证据。两者保留现有实现；Pro 仓库的非 Pro 分支也保留原行为。

## 验证及构建接入

- `tests/test_lock_jobs.py` 为实际 setter 增加 LTE-only 拒绝条件，覆盖两逻辑卡
  的 4G→自动、NSA→4G、延后 EN-DC、早期回放、重置以及真正错误不被隐藏。
  六项新测试通过 dash / BusyBox ash；完整 63 项回归在 dash 下通过。
- `tests/dashboard_lock_jobs.js` 实际执行按钮回调，核对保存偏好与模组读值不同
  时的开关方向、待生效提示、异步完成和中／英／土耳其语。
  同时更新其旧 RPC/漫游测试替身以匹配当前页面接口。
- 经用户授权热部署四个现有文件，回读校验；通过实际 `mu300dash.lock_set` /
  `lock_status` 顺次验证 4G、待生效 EN-DC 关闭、自动恢复后 EN-DC 关闭、EN-DC 开启。
  四项 job 均成功。最终恢复自动及原先 EN-DC 开启状态，卡源及上网卡不变。
- 生产路径仍为 `sources/finish`，未新增守护或构建输入；目标根检查显式收录
  lock、lock-apply.sh 与 locks.js，防止仅热修机器而漏入后续包。

诊断与原文件备份在忽略的 `work/pro-mode-rejection-20261106/`，不作为构建输入。
