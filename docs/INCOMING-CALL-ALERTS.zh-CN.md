# 来电转发和屏幕提醒

短信转发增加默认关闭的“转发来电提醒”，沿用现有共用／按卡独立配置及
Webhook、钉钉、SMTP、本机短信渠道。勾选和取消均进入实际配置 JSON，
使用已保存的模板语言生成来电内容。没有开启当前配置或来电开关时不投递，
不会在之后启用时补发已观察过的电话。本机短信渠道沿用原有费用确认与目标设置。

MU300／Pro 订阅现有 owner 发布的 NR0 通知，再经既有命令队列执行显式
SPACTCARD + CLCC；不打开设备节点，不把 NR0 当控制端口，不从入口推断卡号。
E5 读取原生 ModemManager 观察器的本机事件流，不另加 AT 查询。
订阅应答之后才取首份状态，URC 突发合并为有界刷新；空 CLCC 对已知通话只在
同一事件中补查一次。查询失败保留已有观察，不假造空列表或增加定时重拨。

提醒使用当前板号适配器的卡源映射，含“内置卡／外置卡”及编号；普通无卡源
映射的机型显示 SIM 1／2。F50 Pro 的外置卡与 IMEI 栈交叉对应保持官方映射。
SIP／SIPS／TEL 号码只取号码部分，去域名与参数；隐藏或无有效号码显示未知。
通话生命周期 ID 在投递前落入 root 私有的 RAM 状态，同一通电话只尝试一次，
反复响铃、号码格式变化和观察器重启不重复投递。投递仍由现有转发结果／历史
记录给出成功或失败，不把网络投递当作必然送达。

U30 Pro 原生屏幕增加全屏提醒，含卡源、号码、主题色听筒图标、“忽略”和
“挂断”。忽略只关闭本通电话的提醒，后续响铃不会重新弹出；接通／结束后
自动关闭，另一张卡的新来电仍可显示。保持 PIN、锁屏和底层页面，不提供接听。
挂断重新核对目标栈、通话身份及状态；同栈有多通电话时不执行可能误伤其它电话
的整体挂断。F50 Pro 无屏幕，MU300／E5 本轮不替换其屏幕程序。

生产入口在现有 unisoc-sms-forward 的独立 procd calls 实例，脚本、事件桥、
Python 依赖、翻译和快速更新所需文件均进入跟踪构建路径。离线测试使用模拟
通话、隔离转发渠道和原生屏幕回放，没有拨打真实电话或发送运营商短信。

2026-11-10 在用户授权的 U30 Pro 热部署网页、独立转发实例和原生屏幕程序，
上传前核对原生构建收据与源码 SHA，备份原件并逐个回读校验；转发配置校验和
保持相同，SIP 音频仍就绪。通过合成 incoming／incoming_result 核对实机画面、
关闭及同一生命周期重复消息不会重开，随后清除测试状态并请求恢复真实快照。
此项没有调用 AT 挂断；实体触摸“忽略”／“挂断”和真实转发仍待实呼验收。
空成功响应另有回归，避免无返回体的屏幕 RPC 被误记为失败。

后续实机反馈暴露了 NR0 的发布遗漏：Pro 将 NR0 注册为现有命令 owner，
`cmd_line()` 原来仅主动发布承载及注册通知，来电的 CRING／CLIP／DSCI 等虽然
已收入原日志，却没有进入 ubus。补齐这些严格的自动通知语法，覆盖空闲及
命令收集中，不改变命令响应、队列或控制端口；普通 CLCC 查询回复仍不发布。
回归直接从模拟桥的 NR0 RX 进入真实管理进程，经私有 ubus 和实际两个控制
队列读取明确选卡的 CLCC，再验证两槽转发任务和屏幕快照，重复响铃不重发。
同时拒绝其它端口、查询回复和 AT 回显，保留原有数据承载事件。该修正没有
热部署，也没有发起真实电话或外部投递；此前合成屏幕检查不包含此发布入口。

后续稳定性修正：通知服务统一通过现有 `mu300-at` 客户端等待原 owner 的准入锁，
始终启用 daemon-only，并使用显式 SPACTCARD 和 owner 公布的控制通道。不存在
先尝试 ubus AT、失败再切另一后端的路径。原来的立即 busy 返回会丢掉最后一次
来电／结束提示，这会造成弹窗漏显或残留。空闲仍只阻塞等待事件，不轮询 AT。

拒接前也使用同一事件内的瞬时空列表确认，保留通话生命周期 ID。CHUP 的 OK
仅代表受理；屏幕继续显示处理中，由结束事件的选卡查询确认完成。确认期限
沿用 AT 请求的 8 秒预算，到期只补一次回读，不重复 CHUP，也不伪造挂断成功。
重复点击合并为一个请求，另一通来电出现不能清掉当前请求的忙状态；确认失败
才允许用户显式重试。新增真实 FIFO/owner/ubus 回归覆盖队列占用、两个槽位、
重复点击、延迟释放和对端结束；纯状态测试覆盖空列表、歧义多通话及读回失败。

“每张卡首次拨入，主叫提示无法接通”尚不能仅凭 UI 或不带 SIM 归属的 CEND
判明原因；本轮没有据此改动射频、注册、卡源或用户保存的语音信箱配置。

2026-11-10 的只读重启对照中，两张卡首次拨入均正常响铃，未复现快速拒接。
抓取记录确认卡 0 的来电事件后约 0.18 秒已生成提醒状态，但结束事件后约
19 秒仍没有空快照，直到用户点击旧弹窗挂断才更新；卡 1 的提醒及结束均及时。
这支持队列占用时丢失最后事件、以及对已结束通话错误判失败的独立缺陷；
不是“未接到基带通知”，也不能据此把首通网络拒接宣布修好。现场只监听已有
NR0/ubus，并在结束后经原 owner 读取 CEER/CIREG；没有部署、挂断、接听、
修改射频/卡源/语音信箱或读取短信正文。基带 CEER 仍返回 unknown。
失败报告读取同样短时占用原有 AT 准入锁，所以这轮是带只读查询竞争的现场，
不能声称完全无干扰；它复现了源码中立即 busy 后丢弃结束事件的问题，但不足以
解释或证明此前主叫快速拒接的原因。
