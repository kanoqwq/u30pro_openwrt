# U30 Pro 运行中切换卡源的模式准备

## 原厂证据和结论范围

对照现有原厂资料：U30 Pro LTY B05 的
`work/pro-highrail-20261126/u30-vendor/ril/libimpl-ril.so` 与 F50 Pro B22 的
`work/f50pro-sms-apex/libimpl-ril.so` 逐字节一致，SHA-256 均为
`d0e9fca6cc92489d085fd9adfab75e7abe90986da754a1f1c4edc1849652384a`。
来源版本及提取摘要保存在 `work/pro-highrail-20261126/inputs.json`。
该摘要用于证据追溯，不进入设备运行时匹配或功能门槛。

两份 RIL 的 `processRadioPowerOn`（0x5a050）均先调用 `initWorkMode` 和
`buildWorkModeCmd`（0x57020），发送工作模式后再执行射频开启。
F50 Pro 的实际断言及用户验收见
[F50 Pro 卡源修复记录](F50PRO-CARD-PAIR-INIT-20261127.zh-CN.md)。

此前新增的运行中卡源准备仅覆盖 F50 Pro；U30 Pro 经 SIM 断电换入另一卡源后，
也直接回放并开启 RF，存在相同的源码步骤缺口。本轮没有在 U30 Pro 实机复现
基带断言，因此不将它表述为已确认的实机故障或验收通过。

## 修正

把已验证的模式准备覆盖到两款 Pro 的运行中物理换卡路径。仅在确实需要路由
且目标卡响应 CPIN、用户允许该栈射频时执行；从同一控制 owner 查询实时
`SPTESTMODE?`，保留其现有双栈模式并发送 `SPTESTMODEM`，再执行原有早期回放、
SFUN 4 与 CFUN 完成核对。

不选择固定制式，不设置默认数据卡或移动主栈，不启停另一个栈；原有 GPIO、
SFUN 5/3/2、原厂五秒延迟、错误回退及用户 WAN 意图保持。无变化源、关闭的
射频以及开机初始化路径不新增模式准备。V50 不进入此 Pro 分支。

另同步已在 MU300 回归的查看卡槽保护：自动查看时，锁定、AT 等操作若在
确认期间遇到查看对象改变，要求重新确认；流量页面首次请求先解析实际卡。
只影响网页请求对象，不修改设备射频或卡源策略。

## 回归及交付

1. U30 Pro 新用例验证两种卡源方向、沿用两组不同的实时模式、准备先于回放和 RF。
2. U30 Pro 模式拒绝恢复旧路由、偏好及 WAN；坏回读不得执行 RF 开启。
3. 未变化源、用户关闭的射频、开机路径不增加模式准备。
4. 与原 F50 Pro、U30 Pro 板型及 RF 完成／回退测试合跑，46 项通过。
5. 实际共用查看客户端及异步漫游组件检查初次 SIM2、并发、手动覆盖、失败恢复与分卡写入。
6. 实际普通更新、首次／再次 diff 应用及撤销，保留配置、卡源、按键和插件数据。

前四组主要日志为 `out/build-logs/20261126-185552-u30pro-card-mode-1132/command.log`；
更新交付日志为 `20261126-190228-pro-card-follow-delivery-47734/command.log`，2 项通过。
补充隔离用例、网页与最终产物核对继续记录于同目录体系。

生产文件仍在原受管路径，由 `tools/u30pro-package.py sources/finish` 收录。
不改安装器、内核或模块；两款分别通过自身 profile 组装并核对实际 ZIP 文件。
本轮没有部署或刷写设备。
