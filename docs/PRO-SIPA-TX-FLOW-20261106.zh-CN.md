# Pro 系列 SIPA 停发队列竞态

## 现场证据

2026-11-06，U30 Pro `r20261106.062846-g548eef39-sf86ad627`，
Linux `6.12.94-u30pro-p1`。电脑 USB NCM 网卡只有链路本地 IPv6。
蜂窝接口仍有公网 IPv6、有效默认路由，CID 1 的 `CGACT` 返回激活。
不能据此认定链路真正可用：设备 IPv6 探测返回 `ENOBUFS`，IPv4 探测也无回包。

- `sipa_eth0` 的 `flowctl=true`，发送/接收计数停住。
- 内核 qdisc 查询显示队列积压 1013 个包、450 次丢包、181 次重新排队。
- SIPA sender `left_cnt=4096`，没有耗尽空闲条目；RM 等待标记为零，
  资源都已释放，但网卡队列仍处于停止状态。
- 日志反复出现 `nic tx already out rm flow ctrl`。
- USB 客户端的 RS 到达 LAN，内核记录了上游 RS 发送请求，但没有新 RA 回来。
  发送队列阻塞时，这个发送计数不能证明报文已真正送入基带。

原始只读现场留在本机 `work/u30pro-usb-ipv6-sipa-stall-20261106.txt`，
不作为构建输入。没有以强制路由续期、关闭休眠、定期重拨或定时唤醒队列掩盖问题。

## 确认的代码缺陷

1. RM/data 流控布尔值和 stop/wake 回调没有串行化。CPU A 可以先设置
   “进入”，CPU B 设置“退出”并调用 wake，CPU A 最后才调用 stop。
   后续退出又被旧布尔值判作重复事件丢弃，形成无后续唤醒的队列。
2. `request_resource()` 尚未返回时 GRANTED 可以已经执行；原代码用迟到的
   `-EINPROGRESS` 重新写回等待状态，或者在授权后才投递进入流控通知。
3. sender 的 enter/exit 是两个独立 work；执行顺序不保证等于硬件通知顺序。
   RM 和 FIFO 流控也不能通过“任一退出就唤醒”处理，两者可能重叠。
4. eth/usb 回调共用了全局 IRQ 保存变量，跨 CPU 获取锁时会覆盖其他调用的
   中断状态，应使用调用栈内的变量。

这些缺陷能够解释现场，但未通过运行中插桩证明本次具体是哪一次回调反序。
离线重现与实际修复后长时间使用的验证必须区分。

## 实现与构建

- 每个 NIC 使用自己的 `flow_lock`，串行完成状态快照和 netdev 回调。
  先取 `flow_lock`，短暂取 RM 锁读当前状态，释放 RM 锁后再通知 netdev；
  RM 的授权回调在进入此路径前已释放 RM 锁，不构成反向加锁。
- 所有流控通知只作提示：读取当前 RM 等待状态及最新 FIFO IRQ 状态，
  二者合并决定停发。重复提示也幂等核对队列，不凭旧标记跳过必要唤醒。
- 不覆盖已经完成的授权；立即授权清除等待，申请错误保留原错误并允许后续申请。
- 关闭先在相同锁下标记 NIC 已关闭，再取消重发工作，迟到通知不重新唤醒网卡。
- eth/usb 使用局部 IRQ 保存变量。保留原数据所有权、资源自动休眠和 modem/AT 流程。

改动位于共用的 `sipa_v3` 生产 overlay，覆盖本仓库 U30 Pro / F50 Pro。
来源和修改摘要登记在 `devices/u30pro/adaptations.json`，通过既有内核 builder
及 sources/finish 组包路径进入 Image 和模块；没有新增常驻服务、轮询或定时器。
MU300 和 E5 另按各自现有驱动基线修复同类授权／队列竞态，未复制本仓库驱动。

## 离线验证

`tests/u30pro_sipa_flow.py` 编译真实 RM 申请、授权和流控函数，配合真实线程、
ASan/UBSan 执行 12 项测试：授权提前完成、迟到进入、暂停 stop 回调并并发退出、
两种流控重叠、过期 FIFO work、真正等待、立即授权、错误传播、关闭与重新打开、
多 NIC 隔离、10000 轮并发资源切换，以及生产锁和 IRQ 更新接线。

同时执行 SDIO 恢复、发送流水线、时钟及移植检查，共 44 项通过。
重编 Image/模块，组包根的 248 个模块与构建收据逐一相同。

## 本机验证（用户授权后）

本机 Linux 为 A，Android 为 B。只更新 `boot_a` 和两份实际变化的 AIC 模块，
保留原 ramdisk；不写 Android、GPT、userdata、NV 或 IMEI。写入前后完整回读摘要
相同；原 boot 和模块备份留在电脑，设备端临时传输目录已清除。
启动后 boot 的 48MiB 尾部区域有后续写入；单独核对前 21634890 字节的
header、kernel 和 ramdisk 与新镜像逐字节相同，不用整分区摘要误判启动载荷变化。

- 正常重启成功，boot ID 已改变，两份模块摘要与此次构建相同。
- U30 Pro 自身 IPv4、IPv6 各三包探测均无丢包；电脑指定 USB 公网 IPv6 为源，
  IPv6 三包探测均成功，USB 已取得公网地址和默认路由。
- 八组间隔四秒的 USB IPv6／设备 IPv4 探测全部成功，每组队列均为运行状态。
  这八组探测期间有其他流量，硬件资源计数没有每轮改变，不能称为八次真实
  休眠唤醒测试。后续现场确实观察到 `rc=sc=10`、资源释放和
  `suspend_stage=0x3f`，下一次 IPv6 探测触发重新授权和队列唤醒并收到回包。
- 新一次 USB 客户端 RS 后，LAN 输入 RS 5→6、WAN 输出 RS 7→8、WAN 输入
  RA 7→8、LAN 输出 RA 7→8，默认路由寿命由 65446 秒刷新到 65529 秒。
  包套接字没有捕获到中继 RA，因此此项证据来自接口 ICMPv6 计数和实际路由刷新，
  不把未捕获的报文写成成功抓包。
- 热点已启动；新增 SDIO 状态显示实际 204.8MHz、有效窗口 71/76、调谐失败零次。

当前现场恢复正常，不等于已经通过数小时／多设备压力验收。F50 Pro 使用相同
生产驱动，但本轮没有 F50 Pro 实机验证，也没有重新发布固件 ZIP。
